# Architecture

Groundgraph has four layers: an on-chain program that holds funds and settles markets, services that index and keep it running, a scorer that turns wallet behavior into a signal, and a web app that ties them together. Funds only ever live in the program; every off-chain component is replaceable and none can move user money.

### On-chain program (`programs/groundgraph`)

- Accounts: `Config`, `FeedAllowlist`, `Market` (PDA from creator and nonce), plus per-market PDAs for the USDC vault, the ABOVE and BELOW mints and the LP mint. Mint and vault authorities are the market PDA.
- Instructions: `initialize_config` (gated on the program's upgrade authority), `update_config`, `allow_feed`, `disallow_feed`, `create_market`, `buy`, `sell`, `merge`, `settle_close`, `void_market`, `redeem`, `remove_liquidity`. Touch markets, `add_liquidity` and per-user guards are reserved and rejected with `NotEnabledInThisVersion`.
- Pricing, fees and settlement arithmetic are specified in [AMM.md](AMM.md). All math is checked integer math with u128 intermediates and rounding in favor of the pool.
- Events are emitted with Anchor `emit!` and decoded from `Program data:` log lines by the SDK and the indexer.
- Security checklist and residual risks: [THREAT_MODEL.md](THREAT_MODEL.md).

### SDK (`packages/sdk`)

One TypeScript package used by the API, indexer, keeper, scripts and the web app: quote and fee math (bit-identical to Rust, checked against vectors generated by the Rust tests), account decoders, event parsing, instruction builders that create associated token accounts where needed, a PriceUpdateV2 codec, fair value, the radar formula, formatters and the API contract in `api-types.ts`.

### Services (`services/*`)

- **Indexer** follows program transactions with a persisted cursor, writes trades, positions, market state and price ticks idempotently (keyed by signature and index), reconciles accounts, promotes confirmed rows to finalized, and publishes live deltas to Redis. One leader at a time through a Postgres advisory lock.
- **Keeper** polls Pyth (Hermes when a key is configured, otherwise the on-chain push feeds), computes fair values and realized volatility, and settles or voids markets. A Redis lock per market and a fresh on-chain check before sending make a second instance harmless. It pays fees only.
- **API** serves REST and a WebSocket fan-out, Solana Actions for Blinks, OG images and Sign-In With Solana sessions. It builds and simulates unsigned v0 transactions, enforces trading limits and region rules (never on sell, merge or redeem), and serves rows with `data_source = 'demo-synthetic'` only when `DEMO_MODE=true`.
- Redis keys and channels are defined once in `packages/svc-core/src/redis.ts`. Postgres is the system of record; Redis holds caches, reservations, locks, heartbeats and pub/sub.

### Scorer (`services/scorer`)

Pipeline: source (synthetic, Helius, or on-chain) to wallet graph, five explainable features per wallet, a GraphSAGE embedding trained on a time-split holdout, a head that combines features and embedding into a 0 to 100 score, Louvain clusters with a sybil cap, a force layout for the 3D graph, the per-market radar, and a nightly track record that compares radar Brier against market Brier. It writes to the same Postgres the API reads. Design and measured numbers: [MODEL_CARD.md](../services/scorer/MODEL_CARD.md).

### Web (`apps/web`, `packages/ui`)

Next.js App Router. All server state goes through TanStack Query and the API client in `src/lib/api.ts`; live updates arrive on one WebSocket that reconnects when the session changes. Wallet connection uses wallet-adapter and Wallet Standard. Transactions are signed in the wallet and sent through the RPC; the UI never invents a number: unavailable metrics render a "Building" state, and a global ribbon says "Demo data" when the API runs in demo mode.

## Trust boundaries

| Boundary | What crosses | Why it is safe |
|---|---|---|
| Browser to API | session cookie, requests for unsigned transactions | the API holds no user keys; sessions are SIWS; CORS and CSRF origin are pinned to `PUBLIC_URL`; view sessions are read-only |
| API to chain | simulation and read calls | transactions are only simulated, never signed by the API |
| Keeper to chain | settle and void transactions | any caller could send these; the program validates the oracle account, feed, window and confidence |
| Oracle to program | `PriceUpdateV2` account | owner, verification level, feed id, publish window and confidence are checked on chain |
| Scorer to API | rows in Postgres | demo rows carry a `data_source` label and are filtered unless demo mode is on |

## Data model

The canonical schema is `packages/db/migrations`. Market id is the market account's public key. Every table that can hold demo data has a `data_source` column (`onchain`, `helius-mainnet` or `demo-synthetic`). Outcomes are lowercase `above` and `below` on the wire and in the database. USDC and outcome shares both use 6 decimals.
